Chapter 1
Synopsis
1.1
Abstract
A container’s security posture is declared in a manifest and enforced by the kernel, and
the two are not the same thing. The manifest names a seccomp proﬁle, a capability set
and a Pod Security Standard. What the kernel actually permits depends additionally on
the container runtime and its version, the node’s distribution, kernel build and loaded
modules, the processor architecture, the active Linux Security Module and the Runtime-
Class, none of which the manifest records. Two clusters running an identical manifest
can therefore expose materially diﬀerent kernel attack surface, and nothing in a deploy-
ment pipeline reports the diﬀerence.
The motivating case is CVE-2026-31431 (“Copy
Fail”), a kernel privilege escalation reached through the AF_ALG socket family, which
the RuntimeDefault seccomp proﬁles of containerd and Moby did not deny and which
Pod Security Standards at the Restricted level did not address.
CALIPER is an instrument that measures enforced conﬁnement directly. It runs as an
ordinary, unprivileged container and executes a corpus of 185 argument-level reachability
probes in eight families (socket address families, netlink protocols, io_uring opcodes,
mount ﬁlesystem types, clone and unshare ﬂags, masked and read-only paths, device
nodes and capability eﬀects). Each probe runs in its own forked child, so a probe killed
by a seccomp ﬁlter or hung in the kernel is recorded as a measurement rather than
ending the run. The result is a conﬁnement ﬁngerprint keyed by the environment cell
that produced it. A Go control plane diﬀs ﬁngerprints and classiﬁes every divergence
as architecture-, kernel-version-, runtime-class- or policy-explained; attributes denials to
the mechanism that produced them using errno oracles, capability and security-module
correlation and cell elimination; evaluates a ﬁngerprint against the declared manifest and
against a versioned, cited reference posture; and generates the minimal seccomp change
that closes what it ﬁnds, verifying each closure by probing again.
The instrument was evaluated on six environment cells provisioned as Compute Engine
virtual machines (arm64 and amd64, AppArmor and SELinux, containerd 1.7 and 2.2,
runc, gVisor and Kata Containers) and on a Google Kubernetes Engine cluster that
measures every pull request.
Every success criterion set in the project proposal was
met: policy-explained divergence in 12 of 15 cell pairs; expectation violations in at least
three cells; the AF_ALG case reproduced with an unmodiﬁed probe image and shown
present on one node and absent on another under the same admitted manifest; 220 of 220
attributed denials correct with 1.3 per cent undecidable on a constructed ground truth; 75
of 75 seccomp-attributable ﬁndings closed and veriﬁed; no residual objects after any run;
and a slowest full run of 8.6 seconds against a 60-second budget. Two results are weaker
than those ﬁgures suggest and are stated openly: on the six production cells between 21.6
and 85.0 per cent of denials remain undecidable, and the three-cell expectation criterion
at the restricted tier depends on a single ﬁnding of doubtful weight. The evaluation
also observed two genuine runtime defects, one in gVisor and one in Kata Containers.
Both were public upstream before this report, and neither was reported by this project.
Keywords: container security, Linux kernel, seccomp, conﬁnement measurement, Kuber-
netes, attack surface, gVisor, Kata Containers, errno oracle.

1.2
Problem Statement
Given a container, on a particular node, at a particular moment, what can it actually
reach in the kernel, and why does that diﬀer from what an identically conﬁgured container
reaches elsewhere? Existing tools answer neighbouring questions. Conﬁguration scanners
report what a manifest declares; runtime monitors report what a workload did, which
is a subset of what it could have done; proﬁle generators report what an application
needs, not what its environment permits. None measures enforced conﬁnement, and none
separates a genuine policy diﬀerence from a diﬀerence that the processor architecture, the
kernel version or a sandboxed runtime explains. The project’s problem is to build an
instrument that does both, from inside an unprivileged container, without damaging the
node it measures.
1.3
Motivation in Brief
The AF_ALG case shows the failure concretely. The vulnerability is reached through a
socket address family rather than a distinctive system call, so a ﬁlter at system-call-name
granularity cannot express it.
Published testing found that workloads which satisﬁed
every conventional hardening check were exploitable, and establishing that fact required
hand-built test images and a hand-written proﬁle.
Whether a given node is exposed
depends on the runtime version installed on it: containerd added an AF_ALG deny to
its default proﬁle in May 2026, and a node running an earlier version enforces a weaker
policy than an identically conﬁgured node running a later one. The same happened with
io_uring in 2023. The declared posture is therefore an assertion, and in current practice
it is unveriﬁed. Chapter 2 develops the background and the motivating case in full.
1.4
Objectives
The proposal set eight objectives, all of which were delivered (Table 5.1, Chapter 5):
1. a probe engine with fork isolation, bounded and accounted side eﬀects and precise
verdicts;
2. an argument-granular probe corpus with a committed set of eight families and a spec-
iﬁed deferred set;
3. denial attribution based principally on errno oracles, with a reported conﬁdence;
4. a stable, environment-keyed ﬁngerprint format and a four-class divergence classiﬁer;
5. a versioned, cited reference posture;
6. an evaluator that separates claim violations, expectation violations and undeclared
exposures;
7. a remediation generator emitting minimal argument-level seccomp policy, with closure
veriﬁed by re-probing;
8. an evaluation across at least six environment cells that reproduces the AF_ALG case
unaided.
1.5

• A measurement engine written in Rust as a static musl binary in a scratch image.
It forks a child per probe, waits on a process descriptor with a hard deadline, survives
seccomp kill actions, snapshots six classes of residual kernel state around every probe

committed baseline of its own system calls.

Chapter 2
Background and Motivation
This chapter describes the Linux mechanisms that together conﬁne a container, how
Kubernetes and the container runtimes conﬁgure them, and why the conﬁguration a
workload author writes does not determine what the kernel enforces. It closes with the
motivating case and the problem that follows from it.
2.1
Containers Share a Kernel
A container is not a virtual machine. It is an ordinary group of processes on the host
kernel, given a restricted view of the system by namespaces, restricted resources by control
groups, and restricted kernel access by a stack of independent enforcement mechanisms.
Every system call the workload makes is served by the same kernel that serves every other
tenant on the node. A vulnerability in any kernel code path that the workload can reach
is therefore a potential escape to the host, and the security of a container is, to a ﬁrst
approximation, the size and content of the kernel surface it can reach. Lin et al. showed
with 88 working exploits that the kernel mechanisms which restrict reachable surface
(capabilities, seccomp and mandatory access control) prevent more privilege escalations
than the isolation mechanisms (namespaces and cgroups) do [2]. Measuring that reachable
surface is the subject of this project.
2.2
The Enforcement Mechanisms
2.2.1
Namespaces and control groups
Linux provides eight namespace types: mount, PID, network, IPC, UTS, user, cgroup and
time. Each gives the process its own instance of a global resource. A container runtime cre-
ates a fresh set for each pod (Kubernetes shares the network and IPC namespaces among
a pod’s containers). Creating a namespace from inside a container is itself a privileged op-
eration: clone(2) and unshare(2) with a CLONE_NEW* ﬂag require CAP_SYS_ADMIN,
except for a new user namespace, which an unprivileged process may create where the
kernel and the distribution allow it, and inside which it holds a full capability set. Control
groups (cgroups v2 on every cell measured here) limit and account resources; they conﬁne
resource use, not kernel reachability, and Gao et al. showed that their accounting can be
escaped by work the kernel performs on a process’s behalf outside its group [4].
4

=== PAGE 18
2.2.2
Capabilities
Root’s privileges are split into roughly forty capabilities,
each gating a family
of
operations:
CAP_SYS_ADMIN
for
mounts
and
most
namespace
creation,
CAP_NET_ADMIN for network conﬁguration, CAP_SYS_MODULE for module
loading, CAP_NET_BIND_SERVICE for ports below 1024, and so on [45]. A process
carries four sets that matter here: eﬀective (checked by the kernel), permitted, bounding
(the ceiling across execve) and ambient.
All four are readable without privilege
from /proc/self/status. A hardened workload drops every capability. A capability
check usually sits deep inside the system call, after argument validation and after the
security-module hook, which matters for attribution (Section 2.3).
2.2.3
seccomp-BPF
seccomp in ﬁlter mode attaches one or more classic BPF programs to a process.
At
every system call entry, before the kernel does any work, each program inspects the
architecture, the system call number and the six argument registers, and returns an action:
ALLOW; ERRNO with a chosen error, which makes the call fail immediately; KILL_PROCESS or
KILL_THREAD, which terminate the caller with SIGSYS; TRAP; LOG; or USER_NOTIF, which
defers the decision to a supervisor [44]. Filters are inherited across fork and execve and
cannot be removed. Two properties shape this project. First, a ﬁlter sees register values
only: it can compare a socket family or a ﬂag word, but it cannot dereference a pointer,
so it cannot inspect a pathname, a ﬁlesystem type string or a structure passed by address.
Second, the ﬁlter’s contents are not readable by the conﬁned process; /proc/self/status
exposes only the Seccomp mode (0 none, 1 strict, 2 ﬁlter) and the Seccomp_filters count.
Reading a ﬁlter needs PTRACE_SECCOMP_GET_FILTER and CAP_SYS_ADMIN.
2.2.4
Linux Security Modules
AppArmor and SELinux are mandatory access control modules that place hooks at
security-relevant points inside the kernel: socket creation, ﬁle open, mount, ptrace and
many more. The container runtime loads a proﬁle (AppArmor, by path) or assigns a
context (SELinux, by type and category) to the container. A process can read its own
label from /proc/self/attr/current (and the AppArmor-speciﬁc /proc/self/attr/
apparmor/current) and can tell whether the proﬁle is enforcing. Yama and kernel lock-
down are further, label-less modules that can refuse ptrace and raw hardware access
respectively. Sun et al. observed that because these frameworks are global to the kernel,
containers cannot apply policies of their own [13]; for this project the consequence is that
the LSM in force is a property of the node, not of the workload.
2.2.5
Masked and read-only paths
The OCI runtime speciﬁcation lets a runtime mask paths (maskedPaths) and mount oth-
ers read-only (readonlyPaths) [43]. runc implements a mask of a ﬁle as a bind mount of
/dev/null over it and a mask of a directory as an empty read-only tmpfs. The kubelet
requests a ﬁxed default set for every container: masked /proc/acpi, /proc/asound,
/proc/kcore, /proc/keys, /proc/latency_stats, /proc/timer_list, /proc/timer_
stats, /proc/sched_debug, /proc/scsi, /sys/firmware and /sys/devices/virtual/
powercap; read-only /proc/bus, /proc/fs, /proc/irq, /proc/sys and /proc/sysrq-
trigger. Gao et al. demonstrated that unmasked procfs and sysfs ﬁles leak host-wide
information to containers [3]; the masked set is the runtime’s partial answer.

2.4.2
RuntimeDefault is deﬁned by the runtime
RuntimeDefault does not name a proﬁle; it names whatever the runtime on the node
ships as its default. For containerd [50] that is the proﬁle compiled into the containerd

compiled into the runtime. The contents change between releases, and a node’s runtime
version is chosen by its operating system image, not by the workload author.

A RuntimeClass selects the low-level runtime handler for a pod.
runc conﬁgures the
mechanisms above on the host kernel. gVisor (runsc) interposes a user-space kernel, the

reach the host kernel directly, many interfaces are not implemented, and the version the
workload sees is synthetic [14, 48]. Kata Containers runs each pod in a lightweight virtual
machine with its own guest kernel; an agent inside the guest applies the OCI speciﬁcation

gVisor and Firecracker-style microVMs exercise substantially more host kernel code than
native containers [15]. A measurement under either sandbox is a measurement of the
sandbox’s interface, and comparing it with a runc measurement without saying so would
report the sandbox as policy.
2.5
The Motivating Case: AF_ALG and Copy Fail
CVE-2026-31431, tracked as Copy Fail, is a logic ﬂaw in the algif_aead module, which
implements authenticated encryption for the kernel crypto user API reached through the
AF_ALG socket family. Combined with splice(2), it writes four bytes into the page
cache of any readable ﬁle, enough to modify a set-user-ID binary in memory without
changing it on disk. CISA added it to the Known Exploited Vulnerabilities catalogue on
1 May 2026 [21, 22], and vendors described it as a root privilege escalation across cloud
environments [23, 24]. Three properties of the case motivate this project.
1. It is reached through an argument, not a system call. Any container that may
call socket(2) can attempt it; what matters is the value of the ﬁrst argument. Policy
generated or reviewed at system-call-name granularity cannot express the diﬀerence
between a workload that may create TCP sockets and one that may reach the kernel
crypto API.
2. Conventional hardening did not prevent it. Published testing found that the
RuntimeDefault seccomp proﬁles of both containerd and Moby allowed AF_ALG and
that Pod Security Standards at Restricted did not address it, so workloads that satisﬁed
every conventional check were exploitable. Establishing that required hand-built test
images and a hand-written proﬁle [25].
3. Exploitability depends on the node.
The ﬂaw is in a module.
Whether
algif_aead is loaded, or can be autoloaded by an unprivileged socket call, is a prop-
erty of the distribution’s kernel conﬁguration and module policy, which the workload
author neither controls nor observes. The kernel loads the module for an unregistered

2.7
Why Existing Practice Does Not Detect It
Conﬁguration review compares a manifest with a benchmark.
In the AF_ALG case
the manifest was correct by every benchmark, and the enforcement was weaker than
practitioners believed; a conﬁguration scanner reports no ﬁnding. Runtime monitoring
observes the workload’s system calls as it makes them, and an attack surface that a benign
workload never exercises is invisible to it. Proﬁle generation traces an application and
emits the system calls it used, which answers what the application needs and not what
the environment permits, and does so at system-call-name granularity. A measurement
from inside the container, at argument granularity, is the missing piece, and it needs four
further things to be useful: an identity for the environment it was taken in, a way to
separate policy from architecture and sandbox eﬀects, a way to say which mechanism
produced each denial, and a model of what ought not to be reachable. Those are the
components of CALIPER.

Chapter 4
Literature Gaps
The survey in Chapter 3 leaves the following gaps. Each is stated as an observation about
the existing work and the need it leaves, followed by the part of CALIPER that addresses
it.
• No measurement of enforced conﬁnement.
Observation: Scanners read declarations, monitors observe behaviour, and generators
derive what an application needs. The research literature evaluates conﬁnement with
exploits against chosen conﬁgurations.
Need: A measurement, safe to run on a production node, of what the kernel actually
permits a given container.
Addressed by: the probe engine and corpus (Chapter 7).
• System-call granularity hides the cases that matter.
Observation: Policy generators, the ancestor tools and most published evaluations work
at the granularity of system call names or numbers. The AF_ALG case, raw netlink
protocols, namespace ﬂags and io_uring opcodes are all distinctions within a single
system call.
Need: Probes and remediation at argument granularity.
Addressed by: the argument-level corpus and argument-comparison seccomp rules (Sec-
tions 7.7 and 8.6).
• Results are not keyed to the environment.
Observation: Existing evaluations report per conﬁguration or per platform. Architec-
ture, kernel build and loaded modules, runtime version, LSM and RuntimeClass all
change what is reachable, and none of them appears in a manifest.
Need: A result format whose identity is the environment, with each ﬁeld’s source
recorded.
Addressed by: the environment cell and ﬁngerprint format (Section 8.1).
• Diﬀerences between environments are not explained.
Observation: A naive comparison of an arm64 and an amd64 node, or of a runc and a
gVisor node, reports every diﬀerence as a weakness. No published tool separates policy
diﬀerences from architecture, kernel-version or sandbox diﬀerences.
Need: A classiﬁer that assigns each divergence exactly one explanation.
Addressed by: the four-class divergence classiﬁer (Section 8.2).
• Denials are not attributed to a mechanism.
Observation: Inside a container an EPERM could have come from seccomp, a capability
check, an LSM, a user namespace limit or a masked mount, and the kernel does not
say which. Reading the seccomp ﬁlter needs privilege an unprivileged container lacks.
Without attribution there is no remediation, because the ﬁx diﬀers per mechanism.
Need: Unprivileged attribution with an honest conﬁdence, and the undecidable remain-
der reported as a measured quantity.
Addressed by: errno oracles, correlation and cell elimination (Section 8.3).
• No model of what ought to be unreachable.
Observation: Pod Security Standards stop at Restricted and say nothing about entry

the runtime ships. Comparing a measurement with the manifest alone would have

Chapter 5
Proposed Solution
5.1
Objective
The project builds an instrument that answers, by measurement, what a container can
reach in the kernel on a particular node, explains every diﬀerence between two such mea-
surements, attributes each denial to the mechanism that produced it where that can be
decided without privilege, evaluates the measurement against both the manifest and a
cited model of what ought to be unreachable, and closes what it ﬁnds with the narrowest
seccomp change, veriﬁed by measuring again. The instrument runs as an ordinary con-
tainer with the same conﬁnement as the workload it stands in for: it never needs, and
never asks for, more privilege than that workload has.
5.2
Rationale
The claim is an engineering one. Measuring conﬁnement from inside a container is not
a new idea (amicontained, Houdini). What did not exist is an instrument that does
it at argument granularity, keys the result to the environment, separates policy from
architecture and sandbox eﬀects, attributes denials, and carries the result through to a
veriﬁed remediation. The proposal therefore treats the divergence classiﬁer, the reference
posture and the evaluator as the contribution, and the breadth of the corpus as the
substrate; breadth was the ﬁrst thing to cut when the schedule required it.
5.3
Research Questions
RQ1 Can enforced conﬁnement be measured at argument granularity from inside an
unprivileged container, safely and quickly enough to run on every pull request?
RQ2 Across environment cells that diﬀer in one axis at a time, how much of the measured
divergence is policy, and how much is explained by architecture, kernel version or
RuntimeClass?
RQ3 What fraction of denials can be attributed to their mechanism without privilege,
and how accurately?
RQ4 Does evaluation against a cited reference posture ﬁnd exposures that evaluation
against the manifest misses, as the AF_ALG case suggests?
RQ5 Can the exposures found be closed with minimal seccomp changes, and does a fresh
measurement conﬁrm the closure on every runtime?
5.4
Design Principles
• Measure, do not infer. Every verdict is the kernel’s answer to one call. The engine
stores no interpretation; attribution and classiﬁcation are computed later from the raw
verdicts and the probe’s declared metadata, and anything that cannot be decided is
reported as undecidable.
• Identity is the environment cell. Architecture, kernel version and loaded modules,
distribution, runtime and runtime version, LSM and RuntimeClass are ﬁrst-class ﬁelds
of every result, each with its source.
22

=== PAGE 36
• Reachability, never exploitation. No probe contains exploit code or uses what a
successful call grants. Enumeration interfaces are preferred over execution; io_uring
opcodes are enumerated with IORING_REGISTER_PROBE, and no submission entry is
ever submitted.
• The instrument survives its ﬁndings. Each probe runs in a forked child, so a
seccomp kill or a hang is a recorded verdict rather than a lost run.
• One interface between the halves. The Rust measurement side and the Go analysis
side meet only at the ﬁngerprint format, which lets four people work in parallel against
recorded ﬁngerprints.
• Report what was given up. The corpus is split into a committed and a deferred
set, and every ﬁngerprint lists the deferred probes as unmeasured, so the gap is visible
in every result.

6.3
The Measurement Half
The probe binary is the only code that runs inside the measured container. It is a statically
linked musl executable in a scratch image: no shell, no C library on disk, nothing that
could issue system calls of its own.
On --run it snapshots the environment cell and
the loaded module set, runs every probe of the selected corpus set in its own forked
child, snapshots residual state around each probe, runs the end-of-run janitor, snapshots
the module set again and writes one JSON document to standard output. It interprets
nothing: a verdict is computed from the child’s exit status and the probe’s declared
metadata, and every further reading is the control plane’s. Chapter 7 describes it in full.

6.6
Why Rust for the Engine and Go for the Control Plane
The engine has three requirements that a managed runtime cannot meet. It must fork
before every probe, and a runtime that has started threads cannot fork safely. It must
not issue system calls of its own that pollute the measurement, while a garbage collector
and a scheduler issue them in the background. And it must survive a child killed by a
seccomp KILL action, which requires precise control of what the parent and child each
execute. Rust compiled against musl into a static binary meets all three; CI checks the
engine’s own system calls against a committed baseline (Section 7.4). The control plane
has none of these constraints and needs the container ecosystem’s libraries (Kubernetes
client, GitHub API, Security Proﬁles Operator types), which are written in Go.

output, corpus/index.json, is what the control plane and the freeze-gate checks read.

not distinguished. From outside the child, a probe blocked forever and one that
would have returned just after the deadline are the same observation. The timeout
travels in the ﬁngerprint so that a verdict can be read against it.

exits; the engine measures whether it did. A rollback hook run by the parent would run
under the same ﬁlters (failing the same way, or killing the parent), or under diﬀerent
ones (succeeding where the probe could not and hiding the asymmetry the corpus
exists to measure).

7.2.1
Why fork and not clone
An early version created children with a raw clone system call. musl caches the thread
identiﬁer and delivers abort() and raise() to it with tkill, so a raw-cloned child
that aborted killed the parent. fork() ﬁxes the identiﬁer up in the child, at the cost
of set_tid_address and rt_sigprocmask there before the probe, both already in the
engine’s start-up set.
7.2.2
The exit status is the measurement
The child reports through its exit status (Table 7.2). Linux errno values on x86_64 and
aarch64 stop at 133, so an 8-bit exit status carries every errno, with two values reserved.
7.2.3
Deadlines
The parent opens a process descriptor on the child and waits on it with the raw ppoll
system call, bounded by the probe’s timeout. Using the raw system call means that on
EINTR the kernel hands back the remaining time and the same deadline continues. A test
shows the same 200 ms sleep recorded timed-out under a 50 ms deadline and permitted
under a 2 s one.
7.2.4

issued it. Because that process is the child, the parent sees SIGSYS in the wait status,
records killed and continues. The engine’s test installs a real KILL_PROCESS ﬁlter in the
test thread, so that the parent runs under the same ﬁlter as the probe, as in deployment;
trips it; checks the verdict; and runs two more probes under the same ﬁlter, one of which

failure while setting up a child is recorded as setup-failed or setup-killed, and the

verdict. A run measured with such defects exits with status 3 (--exit-0-on-defects
keeps a Kubernetes Job from retrying, since the defects are in the document).
7.3
Verdict Classiﬁcation
verdict.rs turns how the child ended into one of six verdicts and the raw errno. The
rules, applied in order, are:

1. If the probe’s architecture applicability excludes this machine: not-applicable, de-
cided before anything runs.
2. If the child returned 0: permitted, errno 0.
3. If the child returned the errno its oracle guarantees: permitted, with that errno. The
call reached the point the oracle was built to reach.
4. If the child returned the errno that absence of the entry point produces, and the
kernel dependency says this kernel may lack it (version below since, present_if
path missing, module absent, or the release unparsable): unimplemented.
5. Any other errno: denied. In particular ENOSYS from a system call the kernel imple-
ments is a ﬁlter answering in the kernel’s voice, and is denied.
6. If the child was terminated by SIGSYS: killed.
7. If the deadline expired: timed-out.
8. Any other signal, or a harness fault: not a verdict; the probe is recorded as unmeasured
with the reason.
Two rules are deliberate. A child that died of SIGABRT or SIGSEGV is the probe
crashing, which must not read as a hardened node: a buggy probe on a permissive node
would otherwise look like conﬁnement. And the engine interprets nothing beyond these
rules; which mechanism produced a denial is computed by the control plane.

One side eﬀect is neither descriptor-shaped nor reclaimable. A socket(2) call on an
address family the kernel has not registered makes the kernel request the module for
it, as does an unregistered netlink protocol, a device node whose driver is a module, or
a ﬁlesystem type; the kernel does this with no capability check on the caller, and the
container cannot unload the module afterwards.

(19 socket, 8 netlink, 3 device and 2 mount). The reduced corpus is the same revision
without them; it is the set CI runs on every pull request, and the one to run on a shared
node.

8.1.2
Digest
The producer computes the digest once: it omits digest from the complete document,
encodes it as UTF-8 JSON with object keys sorted, no insigniﬁcant whitespace and no
HTML escaping, hashes the bytes with SHA-256, and preﬁxes the lowercase hexadecimal
result with sha256:. A consumer preserves the supplied digest and never recomputes
it, because a consumer that ignores optional ﬁelds added later could not reproduce the
original bytes. Fingerprints are not signed: the proposal requires signing for the probe
image, so that operators can allowlist a known instrument, and nothing in the threat
model makes a forged ﬁngerprint the attack.
8.1.3
Compatibility
Within a format version, ﬁelds may be added and must be optional; no ﬁeld is removed,
renamed or retyped; no enumeration value is removed; and unknown ﬁelds are ignored.
Anything else is a new format version. Two ﬁngerprints from diﬀerent corpus revisions
are compared over the probe identiﬁers present in both, and a probe present in only one
is reported in a separate corpus-skew section and never classiﬁed: instrument drift must
not be reported as a property of the node.

three stages: the errno oracle, correlation with the process’s own recorded state, and
elimination by the cell. It never reads host state.

8.6.1
Narrowing rather than excepting

family. The remediator therefore replaces a broad socket allow with one masked-equality
allow per family that remains permitted, using a 32-bit mask so that high register bits
cannot bypass the family test, and does the same for netlink protocols. For clone and
unshare it adds a masked-equality condition to the existing allow so that it matches only
when the user-namespace bit is clear. It never adds an allow rule the runtime’s default
did not have. Probes of one family that share a rule (every io_uring probe) are closed by
the ﬁrst rule; the rest are recorded as closed by it.

Chapter 9
Technology Stack
9.1
Overview
The technology choices follow from the two halves of the architecture. The measurement
half must add nothing to the kernel surface it measures, so it is a single static binary with
no runtime and no shared libraries. The analysis half needs the container ecosystem’s
libraries and is written in the language they are written in. Table 9.1 summarises the
stack; the sections below give the reasons.
9.2
Programming Languages
• Rust (probe engine and corpus). The engine must fork before each probe, must
not issue system calls of its own, and must survive a child killed by SIGSYS. Rust
gives direct control of system calls through nix and libc without a runtime, and
compiles against musl into a fully static binary.
The release proﬁle sets panic =
"abort" (a probe child must never unwind), link-time optimisation and stripping.
Probe deﬁnitions are Rust code, so the oracle’s reasoning about kernel code paths sits
beside the call it describes.
• Go (control plane). Fingerprint handling, diﬃng, evaluation, remediation and the
Kubernetes and GitHub integrations use client-go and go-github, and the remedi-
ator emits Security Proﬁles Operator resources whose types are deﬁned in Go. The
JSON shared with the engine uses encoding/json.
• Shell (delivery). Cell provisioning, measurement and the pipeline driver are Bash
scripts checked with shellcheck in CI.

10.2
Provisioning
Each cell is created by cells.sh create cellN, which boots the VM from a pinned
image and runs the cell’s provisioning script in deploy/gce/provision/. Provisioning is
designed so that a cell rebuilt later is the same cell:
• Ubuntu cells read the package archive through the snapshot 20261016T120000Z; the
kernel, AppArmor, libseccomp and the runtime are held, and unattended upgrades are
disabled. Cell 3 version-locks its runtime, policy and kernel.
• Every download (gVisor, Kata, crictl) is checked against a pinned hash.
• Provisioning fails unless the containerd on PATH, the running daemon and runc are the
pinned versions, and unless the cell’s RuntimeClass handler is registered.
• The packages that deﬁne the cell are recorded in /etc/caliper/packages and com-
mitted beside each ﬁngerprint.
• Cells 5 and 6 register two handlers each: the default (runsc, kata) and a variant that
applies seccomp inside the sandbox (runsc-seccomp, which sets gVisor’s oci-seccomp;
kata-seccomp, which sets disable_guest_seccomp = false).
10.3
Measurement Procedure
cells.sh measure cellN <image> reboots the cell ﬁrst, so that modules an earlier run
autoloaded are not recorded as the node’s, and then runs deploy/gce/measure.sh on it.

job.yaml) and runs it through containerd’s CRI with crictl:
• its own network and PID namespaces;
• UID 65534, all capabilities dropped, no_new_privs, a read-only root ﬁlesystem and a
writable /tmp;
• RuntimeDefault seccomp, and the runtime’s default AppArmor proﬁle where AppAr-

• the kubelet’s default masked and read-only paths, taken from the kubelet’s source,
because an earlier version of the request omitted them and left /proc unmasked (a
defect found in review and corrected before any recorded measurement);

Chapter 12
Responsible Use and Disclosure
12.1
Responsible Use
The instrument probes security boundaries, and the proposal made three commitments
in consequence: the corpus contains no exploit code; the instrument is intended only for
infrastructure the operator owns or has written authorisation to test; and a genuine defect
found in a runtime, distribution or managed platform is reported to its vendor under
coordinated disclosure before publication. The ﬁrst is established by the safety review
(Section 7.8). The second is stated in the documentation and printed in every report
the instrument writes. Two further measures make a deliberate run distinguishable from
an attack: the release image is signed with cosign, so admission controllers and runtime
monitors can allowlist its digest, and the reduced corpus omits the probes most likely
to raise alerts, including the AF_ALG probe on which published Copy Fail detection
rules key. On a monitored cluster the motivating case is demonstrated by allowlisting the
signed image and running the full corpus.
12.2
Disclosure Review: Method
The review covered the two sandboxed runtimes, where the measurements diﬀer most from
Linux and where a diﬀerence is most likely to be a defect rather than a conﬁguration choice.
It was carried out in four steps:
1. Every probe permitted under gVisor (cell 5) or Kata (cell 6) was compared with the
same probe on Linux with the same credentials and no seccomp, which is exactly
the ground-truth capability run on cell 2 (UID 65534, no capabilities). A probe
permitted in a sandbox and denied there is a candidate.
2. Because that comparison has no masked paths, every path probe was compared sepa-
rately with cell 2 and with the ground-truth paths run.
3. Each candidate was traced to the runtime’s source at the exact version measured
(gVisor release-20261005.0; Kata Containers 3.14.0, agent and runtime), and checked
against the current development branch and the latest release.
4. For gVisor, the three claim violations were reproduced with the same release in a
disposable virtual machine, as UID 65534 with no capabilities, against a native Linux

gVisor
Of the three claim violations on cell 5, one is a genuine defect, one a deliberate design

before this project ﬁrst recorded it on 2026-10-18: a ﬁx had been proposed in June 2026

12.3.2
Kata Containers
The Kata agent’s masking routine bind-mounts /dev/null over each path in the speciﬁ-
cation’s maskedPaths. A bind of a character device over a directory fails with ENOTDIR,
which the routine treats as success, so masked directories are never masked. With the
kubelet’s default list the eﬀect is that the guest virtual machine’s ACPI tables and
ﬁrmware information are readable from the container; a directory an operator adds to
the list is left unmasked as well. The defect was reported publicly upstream on 2026-11-
01 and ﬁxed the next day by masking directories with a shared read-only tmpfs; the ﬁx
had not reached a release when this report was written. The maintainers handled it as
an ordinary public bug, without an advisory.
12.4
Where the Commitment Was Not Met
Two genuine runtime defects were observed. Neither was reported by this project, and
both were public upstream before this report. The gVisor case is unproblematic: the
defect was public, with a ﬁx proposed, before our ﬁrst recording of it. The Kata case
is the one where the commitment was not met as written. Our cell 6 ﬁngerprint, public
in the repository since 2026-10-18, showed path.masked.proc_acpi and path.masked.
sys_firmware reachable two weeks before the defect was reported upstream. We did not
recognise it as a defect at the time, because the evaluator records both as undeclared
exposures: the posture asserts masks only for /proc/kcore and /proc/keys, and the
evaluator does not treat the kubelet’s default masked paths as a claim. That gap in the
evaluator is listed among the limitations (Section 13.2) and is the ﬁrst change it suggests.
No ﬁnding has an open disclosure window, and nothing in this report is withheld.

notiﬁcation. Every ﬁngerprint lists them as unmeasured. Five posture assertions con-

The privileged helper. Outlined and neither speciﬁed nor built. Attribution rests on

Nothing in the measurement, classiﬁcation or evaluation path was reduced. Three
further departures from the proposal were not planned:
• The cells run on Compute Engine rather than on developer hardware. Compute Engine
supplied native amd64 machines and nested virtualisation for the Kata cell, which the
team’s arm64 laptops could provide only under slow emulation or not at all, and it
made every cell reproducible from a script, at the cost of the cloud dependency the
proposal had wanted to keep oﬀthe critical path.
• The ancestor comparison covers one target on one cell rather than the six-cell study
the schedule allowed for.
• The Security Proﬁles Operator’s acceptance of a generated resource was checked for
cell 2 only.
13.2
Limitations
• The posture is a judgement.
It is ours, cited and versioned, and ﬁndings are
reproducible against a stated revision, but an expectation violation is only as strong as
the assertion behind it. The FUSE ﬁnding on cell 5 shows an assertion whose rationale
does not carry over to a sandbox, and the three-cell criterion at restricted depends
on that ﬁnding.
• A verdict is the kernel’s answer, not proof of eﬀect.
On a reimplemented
kernel a successful call may do nothing (unshare.flags.newtime under gVisor), and
the oracles are written against Linux’s code paths.
• Attribution in production is mostly undecidable on the runc cells with AppAr-
mor and a recent kernel. The ground-truth ﬁgure measures the attributor, not what
an operator will see.
• The classiﬁer has no ground truth.
Its separation of classes was checked by
unit tests and by the per-pair counts matching the axis each pair moves, not against
environments with known causes.
• Single measurements. Each cell was measured once per conﬁguration from a fresh
boot. The verdicts are deterministic for a given cell, but the runtime ﬁgures are single
runs.
• The residual zero is narrow. Only mounts and network namespaces are created
by any probe; the other four classes are covered by the engine’s tests, not by the
evaluation.
• Module autoload changes the host. A full run loads up to 36 modules that remain
loaded for every tenant. The reduced corpus avoids this, at the cost of the AF_ALG
probe.
• Masked paths are not modelled as a claim. The kubelet’s default masks are part
66

=== PAGE 80
of what every pod is promised, but the evaluator does not treat a reachable masked
path as a claim violation, which is how a real Kata defect was recorded only as an
undeclared exposure.
• The corpus is argument-granular only where arguments are registers. A
pathname, a ﬁlesystem type or a structure behind a pointer cannot be ﬁltered by sec-
comp, so the corresponding ﬁndings can be measured but not closed by the remediator.
13.3
Threats to Validity
Internal validity. Every verdict depends on the oracle being right about the kernel’s
code path. Oracles were reviewed against the kernel source and swept for consistency
before the freeze, and two oracle defects were nevertheless found afterwards and corrected
(the io_uring register descriptor on 6.13 and later, and the io_uring setup hook on 6.15
and later). Other version-dependent orderings may exist on kernels not measured. The
cell recordings are at corpus 0.3.0 and the release is 0.3.3; the two give identical verdicts
and errnos on all six cells, so the results hold for the released corpus.
Construct validity. Reachability of an entry point is a proxy for attack surface,
not a measure of exploitability. A permitted AF_ALG socket is exploitable only where
algif_aead can be loaded and the kernel is unpatched; the instrument reports the ﬁrst
and the module state, not the second. The undecidable fraction is deﬁned over all denials,
killed results included, as the proposal speciﬁed.
External validity.
The cells cover two architectures, two LSMs, two containerd
versions and three runtime classes on Ubuntu, Rocky Linux and Container-Optimized OS.
They do not cover other runtimes (CRI-O, Moby, crun), other managed platforms, or
kernels older than 5.14. The attribution ground truth is on a single cell and contains no
SELinux denials.
Reliability. Provisioning pins package versions through an archive snapshot, holds
and hashes, and every metric is regenerated from committed ﬁxtures by a test, so the
reported numbers can be reproduced exactly from the repository; re-measuring a cell
requires a Compute Engine project.
13.4
Lessons Learned
• “The same conﬁnement as a pod” must be checked against what the kubelet
actually does. The ﬁrst version of the cell measurement script omitted the kubelet’s
masked and read-only paths, leaving /proc unmasked in every recording. A review of
the evaluation pull request found it before the results were used.
• Low-level details decide survivability. A raw clone under musl let an aborting
child kill the parent; a core-dump pipe in the host’s crash handler stalled every SIGSYS
kill until the engine made itself non-dumpable; libc::syscall’s variadic seventh ar-
gument carried garbage in its upper bits on x86_64 until full-width casts were used.
Each was found by a test written for the purpose.
• Freeze dates are what make parallel work possible. Freezing the probe speci-
ﬁcation in week 2 and the ﬁngerprint format in week 9 let four people build against
recorded ﬁngerprints; every later change had to be additive.
• Reporting what is undecidable is more useful than a conﬁdent guess. The
production undecidable fractions are uncomfortable numbers, but they point exactly at
the kernel change (the io_uring LSM hook) and the missing component (the privileged
helper) that explain them.

Chapter 14
Conclusion and Future Work
14.1
Conclusion
CALIPER measures what a container can reach in the kernel, from inside the container, at
argument granularity, and explains the diﬀerences it ﬁnds. It runs 185 probes, each in its
own forked child, in under a second on runc and under nine seconds on gVisor, survives
a hardened proﬁle that kills 122 of its children in one run, and leaves nothing behind.
Its ﬁngerprints are keyed to the environment that produced them, and its classiﬁer keeps
architecture, kernel-version and sandbox eﬀects out of the policy count: of 1,057 divergent
probe pairs across six cells, 606 are explained by something other than policy, and the 451
that remain point at real diﬀerences in enforcement, such as io_uring under containerd
1.7 and the absence of seccomp inside gVisor and Kata by default.
The instrument reproduced the motivating case without help.
With the standard
Job, admitted under PSS Restricted, AF_ALG was reachable under containerd 2.2.1 and
1.7.12 and refused under 2.2.7; the manifest was the same, and only the measurement
showed the diﬀerence. Against the manifest alone the case produces no ﬁnding; against
the cited reference posture it is an expectation violation carrying its CVE. Every denial
the attributor decided on a constructed ground truth was decided correctly, and every
seccomp-attributable ﬁnding it generated a proﬁle for was closed and veriﬁed by measuring
again. Along the way it observed two genuine runtime defects that no conﬁguration review
would have found, one in gVisor and one in Kata Containers.
The evaluation also shows where the instrument stops. In production most denials
on a hardened runc cell cannot be attributed from inside the container, because modern
kernels place an LSM hook in front of the very checks the oracles rely on. A successful
call on a sandbox’s reimplemented kernel does not prove the operation took place. The
three-cell expectation criterion at restricted depends on one ﬁnding of doubtful weight.
And the project’s own disclosure commitment was not met in the Kata case, because the
evaluator did not treat the kubelet’s masked paths as a claim. Each of these is stated in
the report as measured, because an instrument for verifying conﬁnement is only useful if
its own claims can be veriﬁed.
14.2
Future Work
The ﬁrst extensions follow from the limits above.
1. Masked paths as claims. Treat the kubelet’s default masked and read-only paths
as part of every pod’s declaration, so that a reachable masked path is a claim violation.
This is a change to the evaluator alone, and it would have ﬂagged the Kata defect on
the day it was recorded.
2. The privileged helper.
An optional DaemonSet with CAP_SYS_ADMIN that
reads the workload’s seccomp ﬁlter with PTRACE_SECCOMP_GET_FILTER would decide
most of the production undecidable fraction, in particular the 52 io_uring denials on
cell 2.
3. The deferred corpus. Implement the 28 speciﬁed probes, starting with the fam-
ilies the posture already asserts against (bpf, perf_event_open, keyctl, userfaultfd,
68

=== PAGE 82
open_by_handle_at), so that those assertions can produce ﬁndings.
4. Sandbox-aware oracles and posture. Mark probes whose permitted verdict is not
evidence of eﬀect under a reimplemented kernel, and qualify posture assertions (such
as the FUSE device) whose rationale does not carry over to a sandbox.
5. More runtimes and platforms. Podman with crun, Moby, CRI-O, EKS and Talos,
to move the runtime axis across implementations rather than versions.
6. Comparison across clusters on every pull request. Measure each change on
several clusters and report the classiﬁed divergence between them in the pull request,
so that a node-image upgrade that weakens RuntimeDefault is caught before it ships.
7. Posture v2 and SARIF. Use the 282 undeclared exposures as input to the next
posture revision (mount types and raw netlink protocols ﬁrst), and emit SARIF so
that ﬁndings appear in code-scanning interfaces.

The Complete Probe Index
Table C.1 lists every probe in corpus/index.json: the 185 committed probes by family,
then the 28 deferred probes. “Isolates” is the oracle’s isolation (seccomp; sec./LSM for
seccomp or an LSM; undec. for undecidable from the errno alone). “G” is the errno the
kernel returns if the call reaches the oracle’s point, and “A” the errno that absence of the
entry point produces, with the encoded absence after a slash for io_uring opcodes. Errnos
are raw numbers, as in the ﬁngerprint: 2 ENOENT, 7 E2BIG, 8 ENOEXEC, 9 EBADF, 14 EFAULT,

EAFNOSUPPORT, 126 ENOKEY. Every committed probe has a 1,000 ms timeout and runs in
a forked child.
